## 三、关键决策与依据（含**否决过的方案**）

> 这一节最贵——避免接手方重走已否决的路。

### 决策 1：开发环境用「VMware + 现有 Ubuntu VM」（方案 C）

- **否决 WSL2（方案 A，计划原本推荐）**：本机 WSL 未安装，安装需管理员权限 + 重启；而 VMware Workstation 17.6 已装、已有一台运行中的 Ubuntu 24.04.3 VM，**零成本可用**。
- **否决 Docker Desktop**：容器内建 cgroup 子树需 `Delegate=yes` 或 `--privileged`，不适合 Wave 0 早期验证（留给 Wave 5 部署联调）。

### 决策 2：前端在 Windows、后端在 VM；跨域走 **Vite dev proxy**

- **否决「后端开 CORS」**：需要为每个响应加 `Access-Control-Allow-Origin`、**额外处理 OPTIONS 预检**、处理凭证配置；而 cpp-httplib 无内置 CORS，得自己写一层。代理则是"一份配置换掉上面全部"。
- **否决「前端也放 VM」**：node 已在 Windows（v24.18.0），VM 未装 node；且前端放 Windows 后浏览器直接访问 `localhost:5173`。

### 决策 3：Wave 3 HTTP 框架选 **cpp-httplib**

- **否决 Boost.Beast**：复杂度高，学习重点不在网络层。
- **否决自研 epoll**：HTTP 解析是安全雷区，且严重偏离本项目主线（沙箱 + 分布式可靠性）。
- **理由**：计划任务 3.4 写的 `req.body` / `json_error(400, ...)` 与 cpp-httplib 的 handler 形态**完全吻合，一行不用改**；OJ 的提交接口是"提交即返回 + 前端轮询"，同步阻塞模型足够。

### 决策 4：接受 Ubuntu 24.04.3 / g++ 13.3.0 的版本偏差

- **否决「装 g++-11 对齐 22.04 基线」**：计划任务 0.4 本就用 `strace` **实测**生成 seccomp 白名单，**不绑定编译器版本**。装旧版编译器是净增复杂度。

## 四、岔路（没走的路，以及为什么）

| 岔路 | 为什么没走 |
|---|---|
| 把代码放 VMware 共享文件夹（hgfs） | 沙箱对**权限模型与 exec 语义极敏感**，共享盘上会以极具误导性的方式失败。源码同步走 git |
| 用 `git bundle` / 手动拷贝同步代码 | 仓库有 remote，git push/pull 链路更干净 |
| 在宿主 Windows 上跑沙箱冒烟 | **物理不可能**——Windows 无 namespace / cgroup / seccomp |
| 进程迁移用 `sleep` 猜时序 | 计划 0.6 的整个存在意义就是**消灭 sleep**，改用管道同步 |
| Redis 留在 5.0（宿主那个 Windows 版） | 5.0 **无 `XAUTOCLAIM`**（6.2 才引入），会让计划任务 2.2 无法实现。VM 内装了 7.0.15 |

## 七、接手方最容易踩的坑

1. **不要在 Windows 上跑 `tests/smoke/`** —— 无 Linux 内核能力，必失败（这是设计使然，不是脚本问题）。
2. **不要用 stale 的 VM IP** —— 曾出现 `192.168.31.11` 这样的过期快照；正确值是 **`192.168.40.128`**（用 `vmrun getGuestIPAddress` 或 `ip -4 addr` 现取）。
3. **不要强杀 `unattended-upgrades`** —— 等它释放 dpkg 锁，比抢它安全。
4. **计划任务 0.4 的产物是 Wave 1 的输入** —— `artifacts/gpp_syscalls.txt` 是编译期 seccomp 白名单的依据，务必保留。
5. **计划原文的任务 0.8 示例有顺序缺陷** —— 原文是「先 XADD，再 `XGROUP CREATE ... '$'`」，那样消费组从流末尾开始，刚发的消息读不到，`XPENDING=0` 是**假通过**。`08_redis_stream.sh` 已改为「先建组(from 0)，再 XADD」并**断言真的读到消息**。
6. **VM 的 `192.168.40.128` 是 DHCP 分配** —— 重启后可能变，配置里引用 IP 时留意。
